Soroban Contract Verification

Sorofy

Proof that on-chain bytecode came from the source you can read.

A deployed Soroban contract is opaque bytes. Sorofy rebuilds it from source in a deterministic, digest-pinned sandbox and byte-compares the result against the network's own hash — then serves that verdict through a free, KYC-free API.

Retroactive path proven Testnet MVP Rust · Axum · Docker Open source · MIT

SCF RFP — Contract Source Verification Service · awarded MVP, now hardening for testnet

01 · The problem

On Soroban, deployed bytecode is opaque.

When a contract is deployed, all that lives on-chain is bytes. There is no programmatic way to confirm that the source an explorer shows actually compiles to those bytes.

What already went wrong

Stellar Lab removed its source-code tab after a malicious WASM was shown receiving a "build verified" badge. Showing unproven source is worse than showing none.

Why SEP-55 isn't enough

SEP-55 uses CI attestations to prove provenance — "a CI ran at this commit." That CI can fetch external code or swap dependencies. It never proves source → bytecode.

SEP-55 gives "a false sense of security."

— OrbitLens, StellarExpert
Ethereum → Etherscan / Sourcify Solana → verified-builds Soroban → no production-grade equivalent

02 · The solution

Don't trust the source — rebuild it.

Rebuild the contract from source in an isolated, digest-pinned container, byte-compare the sha256 against the on-chain hash, cache the verdict, and serve it cheaply. Compute once; every explorer, wallet and CLI just queries.

01 SUBMIT Source + ID Git commit or SEP-58 archive + contract_id.
→
02 RESOLVE Ask the chain Soroban RPC → on-chain WASM hash. The caller never picks the answer.
→
03 REBUILD Sandbox Digest-pinned Docker; compile phase runs --network=none.
→
04 COMPARE sha256 match rebuilt == on-chain, byte for byte.
→
05 SERVE Cache + API verified / mismatch + trust_level, cached in SQLite.
SEP-58 = vocabulary SDF's SEP-58 defines the metadata to reproduce a WASM (bldimg, source_uri, source_sha256). The service, sandbox and integration layer are this project's job — consumed by Explorer · Wallet · Lab · stellar-cli.

04 · Real enforcement, not a flag

The build image is pinned to a registry digest.

For two independent verifiers to agree, they must pull byte-identical build tooling. So a bare tag is refused before any container starts — the image must resolve to a single-arch manifest digest.

bldimg submittedOutcome
sorofy/build-image:rust1.91.1-cli23.2.1 (bare tag) ✕ error — "build image must be digest-pinned", rejected before any container
ghcr.io/…/sorofy-build-image@sha256:cff44167… ✓ verified — 48.7 s, rebuilt == expected == 47d2801e…
Published, single-arch → one manifest digest:
ghcr.io/erdemasik001/sorofy-build-image@sha256:cff44167d2ee90f901c768ccdb75eb5c382c95295f44bcd7ee4b543f0adf9588

Why it matters: a shared digest is the precondition for the multi-verifier model — the same bldimg guarantees the same bytes, so disagreement between verifiers means a real discrepancy, not a toolchain drift.

05 · Why us

The RFP's three hardest requirements are where competitors do least.

The gap is open: no production-grade, multi-verifier, open-source service exists yet. We differentiate exactly on the parts everyone else skips.

Decentralization

02

Retroactive verification

RFP · priority requirement

Trust levels, not a binary

07 · Honest status

What's real, and what's deferred.

Real & proven

  • Retroactive verify byte-for-byte against the on-chain hash
  • Digest enforcement with teeth — bare tags rejected before any container
  • Published GHCR image (single-arch, cff44167…)
  • Auth + rate limiting — bearer token on POST, token bucket + bounded queue, 429 over either
  • Hardened sandbox — mem/CPU/PID/swap caps, --cap-drop=ALL, no-new-privileges, SSRF guard re-validating every redirect hop
  • Operable — /health, /metrics, structured logs, schema migrations, cache snapshots
  • Proven in CI — the real Docker/RPC reproduction suite runs on every merge, not just by hand
  • Live on testnet — https://sorofy.site, TLS-terminated, API on loopback only; 13 verified + 1 deliberate mismatch, 0 errors, avg build 86.5 s
  • Filtered fetch egress — the host firewall now drops the fetch network to every internal range, reinstalled on boot and verified live (metadata and RFC-1918 blocked, crates.io reachable)

Not yet true

  • trust_level hardcoded arbitrary — the allowlist / multi-verifier surface (M2) is where the other tiers come from
  • Single verifier — decentralization is architected for, not yet built
  • No CSP on the explorer — output escaping is tested and holds; the header layer behind it is not there yet (G8)

The engine is done. The differentiation is designed. The path to mainnet is costed — and every number on these slides is a real run, not a mockup.
